# Reusable components for a general financial decision/action agent

Research checked **28 October 2026**, for the 29 October 11:00 Europe/Bucharest submission. Scope: seven repositories, official source files, public GitHub metadata, and npm registry package manifests. **Static inspection only:** no packages installed, third-party code executed, repositories cloned, or browser sessions relaunched. Setup estimates below are engineering judgments, not measured installation times.

## Recommendation

**Superseded on 28 Oct 2026:** the orchestrator is now the Claude Code CLI with allowlisted MCP tools ([ADR 0005](../docs/adr/0005-local-claude-inference.md)); the Vercel AI SDK recommendation below is kept as research history.

Build **one shared financial decision engine for personal and business goals**, using a small Next.js app and Vercel AI SDK's actual tool-approval example as the starting reference. Add **PapaParse** for CSV import. Keep **assistant-ui** as the only optional UI add-on, subject to a short integration timebox; plain React cards plus `useChat` are the fallback. Do not combine multiple agent frameworks.

The shared loop is: clarify goal and missing facts → load relevant profile/ledger/catalog → simulate baseline and alternatives → stress assumptions → explain the trade-off → obtain approval for an exact action bundle → create a local draft/preparation artifact → replan if facts or consent change. Context determines the tool allowlist. A phone buyer gets budget/purchase tools; a homebuyer gets housing-cost and document-preparation tools; a pretzel-shop owner gets stock, invoices, business cash flow, and owner-income tools. All five proposed functions become capabilities available when relevant, not mandatory steps for every person.

With two active teammates, no existing code, and about 24 hours, spend code effort on the shared state, numerical engine, three fixtures, and visible tool execution. A second teammate can build fixtures, test expected outcomes, ask mentors about rules, and prepare the English story/video. Claude/Codex subscriptions are **not evidence of app inference API credits**: secure one working provider endpoint/key separately; model availability and event credits remain unverified.

Use a standalone Next.js App Router project with the small AI SDK example as a **reference**, not a wholesale clone. The inspected runnable-shape reference consists of:

- [Agent with explicit approval policy](https://github.com/vercel/ai/blob/3216f06d0d892b03ad607b4716bbf04056cbfe3d/examples/ai-e2e-next/agent/openai/weather-tool-approval-agent.ts).

Those files use internal example imports, so adapt the pattern into local files rather than claiming they work pasted unchanged. Remove example console logging. The model ID in an example is not evidence that the event account has that model enabled.

Registry reads confirmed these exact published versions and constraints, without installation: [ai 7.0.155](https://registry.npmjs.org/ai/7.0.155), [React adapter 4.0.159](https://registry.npmjs.org/@ai-sdk/react/4.0.159), [OpenAI adapter 4.0.104](https://registry.npmjs.org/@ai-sdk/openai/4.0.104), [Next 16.4.3](https://registry.npmjs.org/next/16.4.3), [React 19.3.1](https://registry.npmjs.org/react/19.3.1), [Zod 4.6.7](https://registry.npmjs.org/zod/4.6.7), [PapaParse 5.7.0](https://registry.npmjs.org/papaparse/5.7.0). Use an installed Node >=22, pin the selected versions, and commit the lockfile. These are **manifest-compatible candidates, not a tested build**.

Use today's [`isStepCount`](https://github.com/vercel/ai/blob/3216f06d0d892b03ad607b4716bbf04056cbfe3d/packages/ai/src/generate-text/stop-condition.ts) API with an explicit limit such as eight steps. Some inspected examples still say `stepCountIs`; follow the pinned package's exported types rather than mixing tutorials from SDK 5/6/7. [ToolLoopAgent reference](https://github.com/vercel/ai/blob/3216f06d0d892b03ad607b4716bbf04056cbfe3d/content/docs/07-reference/01-ai-sdk-core/16-tool-loop-agent.mdx) documents `prepareStep`, `activeTools`, `toolCallConcurrency`, lifecycle callbacks, and runtime context. Use sequential execution for state-changing tools; independent read/simulation tools can run concurrently.

Approval is not a durable workflow store. Keep a server-authoritative session state with profile revision, goal, input provenance, simulation versions, tool events, pending approval, and action outcomes. For a local demonstration an explicit single-process store is acceptable if its reset limitation is stated. Refresh/restart recovery requires a real persisted store; do not claim it from streaming chat alone.

**Important inspected behavior:** [official approval docs](https://github.com/vercel/ai/blob/3216f06d0d892b03ad607b4716bbf04056cbfe3d/content/docs/03-agents/06-tool-approvals.mdx) explain that client-supplied chat history can contain forged approvals. Bind an approval server-side to the exact tool/input/profile revision; the current SDK additionally offers experimental signed approvals. Keep any signing secret server-only. A denial must not trigger repeated requests for the same action. No real sending, purchase, mortgage application, or payment tool belongs in this demonstration.

## Numerical engine: implement a small deterministic module

Use TypeScript pure functions, integer **bani** for RON, bounded safe integer amounts, calendar-day buckets, explicit rounding, and no FX unless rates are supplied. LLMs gather/clarify inputs and select tools; they do not calculate balances, invent prices, infer Romanian tax rules, or certify lending eligibility.

Represent dated cash events once: `eventId, ledgerId, date, amountMinor, currency, category, sourceId, status`. Maintain separate household/business ledgers; an owner transfer is one linked debit/credit pair, not new revenue. Recognized income, invoices, and cash receipts must not be counted as three receipts. Loan drawdowns are cash inflows and debt, not profit; show fees and repayments across the horizon.

For each day: closing cash = opening cash + cash receipts − cash payments. Return minimum cash/date, reserve-floor breaches, debt service, total committed cost, final cash, and a trace back to source events. Run at least baseline and downside scenarios with visible assumptions, such as payment delayed 14 days, income reduced, or quoted rate increased. Call these **stress scenarios**, not calibrated probabilities/confidence scores. Invoice reminders alone never move a receivable's cash date; a negotiated date or simulated assumption must be explicit.

For stock, deterministic quantities/reorder alternatives produce dated supplier payments and order receipts. For personal income, use a declared essential-spend floor and transfer policy. For products, use a small **labelled mock catalog**, normalized cash costs/fees/dates and document requirements; distinguish affordability under assumptions from eligibility and bank approval. For homes, request missing transaction costs or return an incomplete result instead of assuming zero.

CSV is enough for the demo. Use a documented column mapping and review screen; file-size/row caps; accepted/rejected row counts; duplicate IDs; locale-specific decimal/date parsing. Treat invoice descriptions and imported text as data, never model instructions. PDF/document import is an optional later adapter; a manually confirmed structured form is the fallback. No Docling/OCR service or bank aggregator is needed to prove this engine. Those repositories were not inspected in this bounded seven-repo review.

## Narrow tool contracts and visible state

These are proposed contracts, **not existing implementation**. Every tool validates schemas on the server, returns typed errors, and records a tool-call ID/input revision. Imported/mock values carry provenance and `observedAt` or `assumed:true`.

| Tool | Input → output / constraint |
|---|---|
| `loadContext` | `{profileId, goalType}` → relevant ledgers, obligations, missing fields, authorized module list. No inventory/collections tools for a pure homebuyer. |
| `importLedger` | `{fileRef, mapping, locale}` → normalized rows, duplicates, errors, preview revision; user confirms import before it changes scenario inputs. |
| `simulateDecision` | `{profileRevision, horizonDays, candidateActions, assumptions}` → dated cash series, floor breaches, costs, trace IDs, missing facts. Candidate actions come from a server allowlist, not arbitrary executable expressions. |
| `compareProducts` | `{catalogRevision, need, constraints}` → eligible-to-compare mock options, normalized costs, missing eligibility facts, required documents; never returns bank approval. |
| `proposePlan` | `{simulationIds, selectedAlternative}` → versioned action bundle with exact costs, recipients/templates if applicable, dependencies and expiry. Cannot claim execution. |
| `prepareApprovedAction` | `{planId, planRevision, approvalId, idempotencyKey}` → local draft/reminder/purchase checklist/onboarding packet plus `status:'prepared'`. Reject changed/stale inputs and reused approval for a different action. No actual send, application, order or transfer. |

UI: shared goal composer and context panel; current plan; tool activity list with inputs/results; scenario comparison; specific approval card; prepared output. Show operational states such as reading → simulating → comparing → awaiting approval → preparing → complete/blocked. This is observable execution, not a display of hidden chain-of-thought. User edits invalidate dependent simulations and approvals and cause replanning.

## Meaningful demonstration tests for three audiences

All figures below are **synthetic fixtures in RON**, not financial recommendations or verified offers. Test arithmetic deterministically and separately run the live model loop; a prerecorded trace must be labelled replay rather than live execution.

1. **Phone:** cash 9,000; protected reserve 5,000; phone cash price 4,200. Immediate purchase leaves **4,800**, so the agent rejects that option under the stated reserve constraint. A 2,000 phone leaves **7,000**; waiting one month with an assumed net 450 surplus permits the 4,200 phone with **5,250** remaining if price/other facts stay fixed. Test that installments compare full fees/cost and future payments, not just the first payment. No invoice/stock tools should run.
2. **Home:** cash savings 90,000; proposed down payment 80,000 plus assumed closing/moving costs 10,000 leaves **zero**, violating a 20,000 reserve. A mock alternative requiring 60,000 plus 10,000 leaves **20,000**. With monthly income 8,000, essentials 4,500 and payment 2,600, residual is **900**. Reducing income by 1,500 makes it **−600**; the agent must expose the downside and replan. Missing closing costs must produce a question/incomplete result. Neither result implies an available mortgage or lender approval.
3. **Pretzel shop / growth order:** opening business cash 18,000; incremental order receipts 40,000 on day 30; stock costs 20,000 on day 1; fixed bills 11,000 and owner transfer 5,000 on day 7; existing receivable 12,000 paid on day 10. Baseline minimum is **−18,000 on day 7**, despite positive eventual cash. Alternative: assumed customer deposit 16,000 day 0, remaining receipt 24,000 day 30; supplier payment 10,000 day 1 and 10,000 day 35. Business minimum becomes **8,000**, and day-35 closing cash **34,000**, above a stated 5,000 business floor. The owner's 5,000 household credit supports a separate 4,000 essential-spend event, leaving 1,000; the transfer cannot inflate consolidated income. If the customer accepts only an 8,000 deposit, minimum becomes **zero** and the agent must replan. An unconfirmed collection reminder cannot be used to fix that shortfall. Mock financing/product preparation is an available alternative, not a mandatory recommendation.

Cross-cutting acceptance checks:

- Change a bill/date after approval: the old approval is rejected and simulation reruns. Decline the proposed financing action: no application is prepared and no identical retry loop occurs.
- Submit the same approved preparation twice: one artifact/result, using idempotency. Alter tool arguments in the approval request: fail closed.
- Unknown product fee, missing invoice date, mixed currency, ambiguous `1.234,56`, duplicate invoice/payment, and malformed CSV: explicit errors or clarification; no silent zeros or double-counted income.
- Tool timeout/provider failure: visible incomplete state and retry; deterministic fixture mode can still demonstrate calculations, clearly labelled without a live model claim.
- Compare the three golden results to the simulator, test a multi-step live path including one revised assumption and one approval/denial, and verify the English UI shows tool outputs and prepared action status. These are proposed checks; none were run in this research task.

## Competitive/reuse implications and mentor questions

Origin's official article, **updated 8 September 2026**, already claims personalized financial analysis, budgets, major-decision what-if modeling and proactive prioritized Actions. Its article defines Actions as recommendations; it does not establish the exact execution capabilities of its whole product. Therefore **“chat with your money + what-if + proactive advice” is not a defensible novelty claim**. Proposed differentiation to demonstrate: the same personal/business engine with cash-traceable alternatives, explicit constraints, revised assumptions, and a verifiable approval-to-prepared-output loop. This is positioning to test, not a claim that Origin lacks those features. [Official Origin AI Advisor article](https://support.useorigin.com/hc/en-us/articles/39419419459085-What-is-the-AI-Advisor).

Broad supported audience remains the product vision. Initial test/distribution cohorts may be sequenced by task and data accessibility; that is an execution choice, not a declaration that the product serves only SMEs. The stack supports all three demonstrations without a general ERP or a universal legal/credit engine.

The official rulebook, last updated **28 August 2026**, states challenge work starts at the official start, teams retain their IP subject to third-party rights, and teams must secure required licenses/permissions. It does **not explicitly settle reusable libraries/templates versus prebuilt complete projects**, and no mandatory sponsor API appears in that inspected rulebook. Confirm challenge-specific requirements onsite. Ask the organizer/mentor, with the actual repos named: “May we use Apache/MIT SDKs and small public examples, if all goal logic, simulator and product UI are built during the hackathon and reuse is disclosed?” Also confirm whether the sponsor requires an API beyond the rulebook.
